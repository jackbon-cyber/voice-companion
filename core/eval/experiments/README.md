# 记忆检索阈值推导实验

> 这些脚本是**相关性下限 0.529 这个数字的证据链**。
> 没有它们，0.529 就只是一个魔法值 —— 换批数据时没人知道该怎么重算。

## 为什么这些脚本要入库

阈值写在 `MemoryRelevancePolicy.MIN_RELEVANCE_SCORE` 里，
但**这个数字本身不是设计出来的，是测出来的**。

如果只交代码不交实验：
- 换一批数据时，只能靠"感觉调一下"；
- 没人能验证 0.529 是推导出来的还是拍出来的；
- 评审时无法判断它是否过拟合。

## 脚本清单（按推导顺序）

| 脚本 | 回答什么问题 | 结论 |
|---|---|---|
| `pooling_experiment.py` | CLS 池化还是均值池化？ | 记忆 Top-1：CLS 84.6% → **均值 92.3%**；意图分类两者均 100% |
| `intent_pooling_experiment.py` | 换池化会伤到意图维度吗？ | 不会，两者都是 15/15 |
| `verify_pooling.py` | 服务里的向量和本地现算的口径一致吗？ | 一致（否则上面的对比不成立） |
| `distance_distribution.py` | 相关与不相关的距离分布长什么样？ | 有重叠带，无法纯靠全局切分 |
| `threshold_experiment.py` | 距离切在哪最合适？ | 距离 1.10 处覆盖率/精度平衡最好 |
| `holdout_threshold.py` | **阈值该在哪批数据上定？** | **留出集**（问句与评测集不重合、语料相同）→ 区间 (0.5268, 0.5313] |
| `discriminability.py` | 有没有比绝对得分更好的判据？ | 五种相对判据**全部不可分**（领先幅度反向重叠） |
| `margin_probe.py` | 领先幅度到底能不能用？ | 不能：答错样本的领先幅度比多数答对样本还大 |
| `paraphrase_noise.py` | 检索的噪声底有多大？ | 同义改述之间的分差有限 |
| `query_instruction.py` | 检索侧加 BGE 官方指令前缀有改善吗？ | **没有**：Top-1 从 12/13 掉到 11/13，故不采用 |
| `cross_validate_floor.py` | 三份互不重合的数据上交叉验证 | 缝隙稳定但很窄（余量 0.0023） |
| `finalize_floor.py` | 定稿阈值，并给出错误代价与覆盖率代价 | **0.529**（区间中点） |
| `gate_numbers.py` | 三个门禁数分别定多少？ | 作答准确率 0.95 / 覆盖率 0.75 / 编造率 0.05 |
| `policy_on_chroma.py` | 在真实 Chroma 上验证这套策略 | 成立 |
| `policy_experiment.py` | 策略整体对作答质量的影响 | 成立 |
| `answer_probe.py` | 作答维度有哪些失败样本？ | 见失败明细 |
| `e2e_query_probe.py` | 相关性下限对端到端断言有影响吗？ | 无负面影响 |

## 关键结论摘录

**留出集推导**（`holdout_threshold.py`）：

```
答得对时的最高得分下界 = 0.5313
库中无答案时的最高得分上界 = 0.5268
=> 合法取值区间 (0.5268, 0.5313]，取中点 0.529
```

**为什么不用评测集推导**：评测集（`core/eval/memory_answer-eval.txt`）
就是门禁要用的那批数据。在它上面挑一个"能过线"的阈值是**拿答案调答案**，
换批数据立刻失效。留出集的**语料与评测集相同、问句全部重写**，
因此阈值是独立推导出来的。

**被实测否掉的方案**（留在仓库里是为了说明"为什么没有"）：

1. **区分度判据**（第一名与第二名得分差太小就拒答）—— 不可分，领先幅度反向重叠。
2. **查询侧加检索指令前缀** —— Top-1 从 12/13 掉到 11/13，代价大于收益。
3. **更小的下限 0.476** —— 覆盖率更高，但 14 条答不上的问句里有 11 条被当成答案，
   **系统开始编造**。

## 脆弱性

0.529 两侧只有 **0.0023** 的余量，样本量只有 13 + 14 条。
这是**当前实测下的取值，不是普适结论**。

评测集或留出集扩充后**必须重跑 `holdout_threshold.py` 并重新推导**，
不能沿用现值。检索能力提升（更大的嵌入模型、混合检索、query 改写）
会让缝隙变宽，届时应**上调覆盖率门禁、而不是下调相关性下限**。
