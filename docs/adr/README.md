# 架构决策记录（ADR）

> 每条记录一个**有取舍**的技术决策。格式固定：选项 / 选定 / 理由 / 未选原因 / 代价。
>
> **ADR 记的是"为什么"，不是"是什么"。** "是什么"看代码和
> `docs/interface-contract/README.md`；ADR 回答的是"当初为什么这么选，
> 以及什么情况下应该改回来"。
>
> 状态取值：`已采纳` / `已废弃` / `已替代`。
> 决策生效后不修改原记录 —— 要改就写新记录并把旧记录标为"已替代"。

## ADR-001 · 仓库形态：独立仓库

**状态**：已采纳 · 2026-11-13

### 背景

项目有两个目标：求职作品（需要独立可展示、干净、可复现）与公司落地
（需要私有部署层、监控、GPU 编排）。两者放在一个仓库里会互相污染。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 独立仓库** | `d:\myproject\voice-companion` 单独成仓，`deploy/` 通过 `.gitignore` 排除 |
| B. monorepo | 与 `agent-memory-kb` 等放同一仓库 |
| C. 单仓库 + 多分支 | 开源分支与私有分支分离 |

### 选定

**A. 独立仓库**。

### 理由

- 求职作品需要**一个能 clone 下来就跑的干净仓库**。混在 monorepo 里，
  评审者要自己找"哪些是本次交付的"。
- 私有部署层不该出现在开源仓库的 git 历史里 —— 即使后来加 `.gitignore`，
  历史里的文件仍可被检出。
- 独立仓库让"开源部分"有明确的边界定义，而不是靠约定。

### 未选其他选项的原因

- **B（monorepo）**：与 `agent-memory-kb` 共享记忆资产确实方便，
  但让"开源部分"的边界消失。资产共享用**只读复制**解决即可，
  不值得用整个仓库结构去换。
- **C（多分支）**：私有代码与开源代码在分支间同步是持续负担，
  且 git 历史会保留私有内容。

### 代价

- 跨仓库引用需要用相对路径或 submodule，IDE 体验略差。
- 记忆资产靠复制而非依赖管理，更新时要手动同步。
  *缓解*：复制方向是单向的（从 `agent-memory-kb` 复制到本仓），
  且本仓不得修改副本的来源代码。

### 什么情况下应该重新评估

当需要与 `agent-memory-kb` 频繁联动发布（例如记忆 SPI 每次改动都要同步两个仓库），
复制方式会成为负担。届时考虑改用 submodule 或把记忆 SPI 独立成第三个包。

## ADR-002 · 分层按"可复现性"切

**状态**：已采纳 · 2026-11-13

### 背景

常见的三仓切法是"开源 / 参考实现 / 私有"。但这个切法回答不了一个问题：
**哪一层应该进开源仓库？**

### 选项

| 选项 | 说明 |
|---|---|
| **A. 按可复现性切** | 能独立复现核心能力（协议、端侧模拟端、云端骨架、评测门禁）→ 开源；只在本司环境成立的 → 私有 |
| B. 按"开源/私有"切 | 与常见开源项目结构一致，但无法回答"什么该开源" |
| C. 按"成熟度"切 | 成熟的开源，不成熟的不开源 |

### 选定

**A. 按可复现性切**。

### 理由

求职作品的核心要求是"**十分钟内跑通**"。如果核心链路依赖公司的 GPU 集群、
内网网关或私有凭据，评审者根本跑不起来 —— 作品集就失去了说服力。

按可复现性切，能得到一个明确的自检问题：
**"把这一层交给一个没有公司资源的人，他能跑起来吗？"**
跑得起来的进开源仓库。

### 未选其他选项的原因

- **B**：只是换了个说法，没解决"什么该开源"的判断依据。
- **C**：成熟度会变，开源/私有边界会反复移动，对外承诺不稳定。

### 代价

- `deploy/` 里的内容**永远得不到开源社区的审视**，质量靠内部保证。
- 需要有人明确维护"可复现性"这条判据，否则边界会慢慢模糊。

### 什么情况下应该重新评估

当产品的核心能力本身必须依赖私有资源（例如必须用公司的专用模型服务才有价值），
"可复现"就不是正确的判据了。届时应显式改判，并接受作品集需要额外说明。

## ADR-003 · 云端 Java + 端侧 Python

**状态**：已采纳 · 2026-11-13

### 背景

云端与端侧都要实现同一套协议，需要决定技术栈。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 云端 Java（Spring Boot）+ 端侧 Python** | 两侧各自用生态最顺的语言 |
| B. 全 Python | 统一语言，但云端侧要重造 Java 生态已有的轮子 |
| C. 全 Java | 端侧模型推理生态弱，且 PC 模拟端迭代慢 |
| D. 云端 Go + 端侧 Python | 更贴近云原生，但公司 Java 资产无法复用 |

### 选定

**A. 云端 Java（Spring Boot 3.3.5 / Java 21）+ 端侧 Python**。

### 理由

- **云端必须复用公司已有的 Java 资产**：`agent-memory-kb` 的 Chroma 与记忆 SPI
  都是 Java 的。改成 Python 意味着那部分资产全部重写 ——
  而记忆装配恰恰是这类产品最核心也最难重写的部分。
- **端侧必须用 Python**：端侧要跑 `faster-whisper`、`llama-cpp-python`、
  `paho-mqtt`，这三个都是 Python 生态第一梯队。端侧用 C/C++ 写胶水层
  只会增加工作量，不增加能力。
- **两侧不共享代码，只共享协议**。这是 ADR-007 的直接推论：
  跨语言反而逼着协议设计得更严谨，因为没有"顺手改一下"的余地。

### 未选其他选项的原因

- **B（全 Python）**：放弃公司已有的记忆资产，且 Java 侧的 AgentScope 生态用不上。
- **C（全 Java）**：端侧模型推理在 Java 生态里选择少、性能差。
- **D（Go）**：公司的技术栈是 Java，引入第三种语言增加维护面。

### 代价

- **协议是跨语言的，两侧校验实现必然有差异风险。**
  *缓解*：两侧共用同一份 schema 与同一批样例，
  并由 `validate-protocol.ps1` 与跨语言一致性测试守住。
- 端侧 Python 侧做嵌入式部署（真机）需要交叉编译，
  这也是 `device-ref/` 单独存在的原因。

### 什么情况下应该重新评估

若端侧模型生态发生重大变化（例如端侧推理统一到 ONNX Runtime 且 Java
绑定成熟），或公司云端栈从 Java 迁移，则重新评估。

## ADR-004 · 端侧 ASR 用 `faster-whisper`

**状态**：已采纳 · 2026-11-13

### 背景

端侧需要本地语音识别，PC 模拟端与真机都要用。

### 选项

| 选项 | 说明 |
|---|---|
| **A. `faster-whisper`** | 基于 CTranslate2 的 Whisper 实现，CPU 可跑，带 VAD 预处理 |
| B. `whisper.cpp` | C/C++ 实现，生态广，Python 绑定质量一般 |
| C. 云端识别 | 端侧不做识别，全靠云端 |
| D. 厂商 SDK | 特定芯片厂商的识别 SDK |

### 选定

**A. `faster-whisper`**。

### 理由

- **纯 Python 依赖**，与 ADR-003 的端侧语言决策一致，集成成本最低。
- **CPU 可跑**，不需要 GPU。求职作品的硬指标是"没有专用硬件也能跑"。
- **自带 VAD 预处理**（Silero VAD），端侧本来就需要 VAD，
  用它能省掉一路模型。
- 模型权重与上游 `openai/whisper` 兼容，转换生态成熟。

### 未选其他选项的原因

- **B（`whisper.cpp`）**：性能更好，但 Python 绑定不成熟，
  且需要自己编译，破坏"clone 就能跑"的承诺。
- **C（云端识别）**：违背"零硬件可跑通"，且断网就完全不可用 ——
  与"降级到最小档仍可应答"的设计直接冲突。
- **D（厂商 SDK）**：与具体芯片绑定，无法在 PC 模拟端复用，
  与"PC 模拟端是设备侧的行为参考"这一定位冲突。

### 代价

- 识别质量与速度不如 `whisper.cpp`。
- `faster-whisper` 在 Python 3.13 上需要确认 wheel 可用；
  本机实测 3.13.7 可用，3.10 因 `chromadb` 构建失败而未采用。

### 什么情况下应该重新评估

当端侧真机必须达到某个具体的识别延迟指标，或需要支持流式识别
（`faster-whisper` 的流式能力弱于 `whisper.cpp`）时。

## ADR-005 · 端侧 LLM 为可选增强

**状态**：已采纳 · 2026-11-13

### 背景

端侧需要兜底对话能力。是否必须依赖本地大模型？

### 选项

| 选项 | 说明 |
|---|---|
| **A. LLM 可选 + 话术库兜底** | 有模型用模型，没模型用话术库 |
| B. 必须有本地 LLM | 模型是硬依赖 |
| C. 只用话术库 | 不用 LLM |
| D. 全部靠云端 | 端侧不做对话 |

### 选定

**A. `llama-cpp-python`（Qwen2.5-0.5B Q4_K_M）为可选增强，
`PhraseBankDialogEngine` 兜底**。

### 理由

- **"零硬件可跑通"要求没有任何硬依赖**。模型权重 400MB、
  `llama-cpp-python` 在部分环境无匹配 wheel —— 这两条都会让
  评审者在第一步就卡住。
- **对话中断比对话平庸更糟**。模型加载失败时如果直接报错，
  整个陪伴体验就没了；话术库至少能回应。
- 0.5B 的 Q4 模型在 CPU 上推理本身就慢（秒级），
  对陪伴场景的实时性帮助有限，不值得设为硬依赖。

### 未选其他选项的原因

- **B**：把环境问题变成功能可用性问题。
- **C**：话术库没有上下文理解，多轮对话会明显重复。
  *保留*：它是兜底，不是主路径。
- **D**：断网即失能，与降级设计冲突。

### 代价

- 用户在不同机器上得到的对话质量不同。
- 两条路径的行为差异需要测试覆盖（`test_engine.py` 断言回落不中断）。

### 什么情况下应该重新评估

当有了明确的端侧生成速度指标（比如 P95 生成耗时低于某值），
且能在目标硬件上稳定达成 —— 那时把 LLM 从"可选"提升为"推荐"，
并把模型清单纳入部署手册的必备项。

## ADR-006 · 模型权重不入库

**状态**：已采纳 · 2026-11-13

### 背景

端侧模型（Whisper base 约 150MB、Qwen2.5-0.5B Q4 约 400MB）要不要进 git。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 不入库，走 `fetch-models.ps1` 按需下载** | 仓库轻量，权重走 HuggingFace 镜像 |
| B. 用 Git LFS | 走 LFS 存储 |
| C. 入库 | 直接提交 |

### 选定

**A. 不入库**。

### 理由

- 仓库要能快速 clone。700MB 权重的 clone 体验与"作品集"的目标背道而驰。
- 权重有上游版本管理，跟进上游更新比固守一份旧副本更安全。
- 走镜像（`hf-mirror.com`）解决直连不可达的问题。

### 未选其他选项的原因

- **B（Git LFS）**：仍需 clone 时下载全部 LFS 对象，且额外依赖 LFS 服务。
- **C**：同上，且会让 git 历史不可用。

### 代价

- 首次运行多一步下载。
- **镜像不可用时脚本会失败** —— 因此脚本对每个模型给出明确的手动下载指引，
  且两个模型都缺失时端侧仍可降级运行（见 ADR-005）。
- 下载的文件必须校验完整性，否则"下载损坏"会表现为"模型效果差"，
  极难排查。因此 sha256 记入 `core/models/SHA256SUMS`，下次运行即强制校验。

### 什么情况下应该重新评估

当需要保证离线环境可用且不便联网时，应改为内网制品库分发，
并保留 sha256 校验机制。

## ADR-007 · 协议 schema 只有一份

**状态**：已采纳 · 2026-11-14

### 背景

端云两侧用不同语言（ADR-003），协议定义天然有"写两份"的风险。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 一份 JSON Schema，两侧各自读** | 事实来源唯一 |
| B. 两侧各写一份定义 | 各自方便 |
| C. 用 IDL（Protobuf / Thrift）代码生成 | 类型更强 |

### 选定

**A. 一份 JSON Schema 放在 `core/protocol/schema/`，Python 与 Java 各自读**。

### 理由

- **契约的漂移是跨语言项目最常见的缺陷来源**。写两份定义，
  迟早会出现"一边加了字段另一边没加"，而且这类不一致在联调时才暴露。
- JSON Schema 直接就是 JSON，**不需要代码生成步骤** —— 改完 schema 立即生效，
  两端都读同一个文件。
- **校验器是现成的**：Python 用 `jsonschema`，Java 用 `networknt:json-schema-validator`，
  都原生支持 Draft 2020-12 与 `$ref`。

### 未选其他选项的原因

- **B**：漂移不可避免，且需要额外的一致性检查来发现漂移 ——
  那等于又写了一份定义。
- **C（IDL）**：类型更强，但引入代码生成与构建耦合；
  且协议里有大量**条件必填**（如 `type=end` 时 `reason` 必填），
  JSON Schema 的 `if/then` 表达这类规则比 IDL 更自然。

### 代价

- **两侧的 `$ref` 解析行为可能不一致**。已实测踩过两次：
  - Python `jsonschema` 会把相对 `$ref` 当远程 URL 去下载；
  - Java `networknt` 同样会尝试下载。
  *缓解*：Python 侧用 `referencing.Registry` 把协议 URI 前缀映射到本地资源；
  Java 侧用 `JsonSchemaFactory.getInstance` 的 `schemaMappers` 做同样映射。
  两侧都有测试守住"离线不联网"。
- **JSON Schema 的校验性能低于编译型 IDL**。对当前消息体量不构成问题。

### 什么情况下应该重新评估

当协议消息数量超过数百条，或需要复杂的多态/继承结构时，
JSON Schema 会变得难以维护。届时应考虑 IDL 或至少把 schema 拆分成多个模块。

## ADR-008 · 降级与回升都逐级

**状态**：已采纳 · 2026-11-14

### 背景

网络质量会波动。端侧需要在弱网/断网时降级，在恢复后回升。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 降级与回升都逐级** | 一次只动一档 |
| B. 降级逐级、回升一步到位 | 恢复快 |
| C. 降级与回升都一步到位 | 响应最快 |
| D. 不回升 | 降了就不升 |

### 选定

**A. 降级与回升都逐级**，且**连续失败/连续成功计数器互斥重置**。

### 理由

- **网络抖动会让状态反复横跳**。断网时如果"一次成功就回 `NORMAL`"，
  端侧会在几秒内反复切换档位，每次切换都伴随配置变更与重连开销 ——
  用户感受到的是"机器人一会儿正常一会儿卡"。
- **连续计数器互斥重置**：失败计数清零时成功计数也清零，反之亦然。
  这样一次失败后必须有**连续**的成功才能回升，避免"失败-成功-失败-成功"
  的交替把端侧卡在中间档位。
- **判定不依赖云端心跳**：等心跳确认的降级会让断网时端侧仍在做无谓的上行重试。

### 未选其他选项的原因

- **B**：回升一步到位在稳定网络下没问题，但在抖动网络下等于没有回升控制。
- **C**：降级一步到位的问题是：从 `NORMAL` 直接掉到 `MINIMAL` 会让用户
  突然失去所有能力，体验断崖式下降。
- **D**：网络恢复后不回升，等于一次网络抖动就永久降级。

### 代价

- 网络恢复后需要几轮成功才回到正常档位，用户会感到"恢复得慢"。
  这是有意的取舍：宁可慢，不可抖。

### 什么情况下应该重新评估

当实测显示逐级回升的恢复时间超过用户可接受阈值，
且抖动场景的横跳问题已有其他解法（例如加入迟滞带）时。

## ADR-009 · 百分位用最近秩法

**状态**：已采纳 · 2026-11-14

### 背景

端侧要报 P95 延迟。不同库的分位数算法不同，结果可能差几个百分点。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 最近秩法** | `ceil(q * n) - 1` |
| B. 线性插值法 | numpy 默认 |
| C. 自己造一套 | 无 |

### 选定

**A. 最近秩法**，与上游 `agent-memory-kb` 的 `QualityEvaluator.percentile95` 一致。

### 理由

- **跨工程的数字必须能对上**。同一个评测集，在两个工程里算出不同的 P95，
  那两个数字就没有可比性 —— 而这个项目的记忆层就是要复用 `agent-memory-kb`，
  两边的指标必然被放在一起看。
- 最近秩法**只取实际存在的样本值**，没有插值出来的"不存在的值"。
  对延迟指标这更诚实。

### 未选其他选项的原因

- **B（线性插值）**：与上游口径不一致。对 100 个样本，
  线性插值的 P95 是 95.05，最近秩是 95 —— 差得不多，
  但**两份报告摆在一起时这个差异会被当成 bug 查半天**。
- **C**：纯属添乱。

### 代价

- 与 numpy/pandas 的默认结果不同，使用者需要知道用的是哪种。
  *缓解*：代码里写了注释说明口径与理由。

### 什么情况下应该重新评估

如果上游 `agent-memory-kb` 改了算法 —— 应当**跟随上游**，
而不是坚持本仓的算法。两边口径不同比哪边"更对"更重要。

## ADR-010 · 门禁退出码约定

**状态**：已采纳 · 2026-11-13

### 背景

评测门禁脚本要被 CI 调用，退出码必须能表达"为什么失败"。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 多退出码区分失败原因** | 0 通过 / 1 门禁未达标 / 2 环境问题 / 3 结果解析错误 |
| B. 统一 0/1 | 简单 |
| C. 只用输出文本判断 | 无需约定，但不可靠 |

### 选定

**A. 退出码区分失败原因**：

| 码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 门禁未达标（指标劣于阈值） |
| 2 | 环境问题（依赖服务未就绪、模型缺失等） |
| 3 | 结果解析错误（报告格式与预期不符） |

### 理由

- **CI 要能区分"代码有问题"与"环境有问题"。** 统一 0/1 时，
  网络抖动导致的依赖服务不可用会伪装成"质量不达标"，
  让人去查代码 —— 查半天发现是环境。
- **退出码比输出文本可靠**。解析日志文本做判断在格式一变就失效。

### 未选其他选项的原因

- **B**：丢失了"是环境还是代码"的信息。
- **C**：日志格式一变就失效，且无法被 CI 可靠消费。

### 代价

- 脚本要显式区分各类失败，增加实现复杂度。
- 调用方必须知道每个码的含义。

### 什么情况下应该重新评估

当新增一类失败原因时（例如模型推理超时），可能需要扩展码位 ——
届时应评估是否该改为"码位 + 结构化输出"（如同时输出 JSON 报告），
避免码位无限扩张。
