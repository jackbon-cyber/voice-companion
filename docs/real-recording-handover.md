# 真人录音接入 —— 交接说明

> 面向**拿到录音的人**。目标是：录音到位后，一次跑通，口径全部对上。
>
> 这份说明是"交给下一棒"的交接单，不是教程。
> 详细的录音要求见 `core/eval/recordings/README.md`。

---

## 0. 现在是什么状态

| 项 | 状态 |
|---|---|
| 接入能力（代码） | **已就绪**，已提交并通过测试 |
| 真人录音（数据） | **未取得** —— 这是唯一缺的一环 |
| 端侧报告当前口径 | clean 参与判定；mild / noisy 标注为「音频为 TTS 合成，不作门禁依据」 |
| 拿到录音后 | mild / noisy **自动升级**为门禁条件，无需改代码 |

**代码侧不需要任何改动**。录音放进目录，评测自己认。

---

## 1. 你要交付的东西

**14 个 WAV 文件**，放进 `core/eval/recordings/`。

- 内容：把 `core/eval/asr-eval.txt` 里的 14 条参考文本各读一遍
- 格式：16-bit、单声道 WAV（采样率任意，评测会自动重采样到 16 kHz）
- 命名：**不要自己起名**，用命令生成
- 体积：几十 MB 量级，不入库

---

## 2. 怎么录（要点）

| 要点 | 为什么 |
|---|---|
| **安静环境** | 评测的噪声条件是**程序叠加**的。录音里自带的环境噪声会与叠加噪声混在一起，标称信噪比失真，数字不可解释。 |
| **正常语速、正常语调** | 平板念稿式的语调会让准确率虚高。 |
| **同一人读完全部 14 条** | 不同人的音色差异会让准确率波动，混着录无法归因。 |
| **每条读完即可** | 前后留 0.5 秒静音；评测会自行切分语音段。 |

## 3. 怎么命名

```powershell
cd D:\myproject\voice-companion
F:\tools\python313\python.exe -m core.eval.audio_source --list
```

输出形如：

```
今天天气真不错            -> recording_b37014d20710cdb6.wav
我最近在准备期末考试      -> recording_d7bdebbc7f5bb39c.wav
...
```

**照抄右边的文件名**。哈希是算出来的，手写必错。

## 4. 怎么验

```powershell
# 4.1 确认 14 条都被认出来
F:\tools\python313\python.exe -m core.eval.audio_source --check
```

期望输出：

```
参考文本总数：14
已有真人录音：14 条
缺录音（将回退 TTS）：0 条
```

> 只要有 1 条缺，评测就**不会**把 mild / noisy 升级为门禁条件
> —— 规则是「全部样本都来自真人录音」才升级，混着算的准确率没有可解释性。
> 所以宁可先补齐再跑，不要分批录。

```powershell
# 4.2 重跑端侧评测（也可以跑完整评测，见第 5 节）
F:\tools\python313\python.exe -m core.eval.edge_eval --report core/eval-edge-report.md
```

看报告的**「音频来源」列**：

| 期望 | 含义 |
|---|---|
| `真人录音 14` | 成了 —— 录音被正确使用 |
| `真人录音 13 / TTS 合成 1` | 有一条没对上，回去查文件名 |

## 5. 到位后要重跑什么

```powershell
# 5.1 完整评测（云端五维 + 端侧 ASR + 门禁判定）
powershell -ExecutionPolicy Bypass -File core\scripts\eval.ps1
```

这一条就够 —— 它会重生成 `core/eval-report.md` 与 `core/eval-edge-report.md`。

**不要**单独跑云端评测来"验证录音接入" —— 录音只影响端侧维度。

## 6. 数字会怎么变（预期）

拿到录音后，**门禁判定范围扩大**：

| 条件 | 现在（合成音） | 拿到录音后（真人） |
|---|---|---|
| clean 30 dB | 85.7% **参与判定** | 参与判定（数字会变，以真人音为准） |
| mild 20 dB | 64.3% 参考值 | **参与判定** |
| noisy 10 dB | 28.6% 参考值 | **参与判定** |

**两件事要预期到**：

1. **数字会变，且很可能变差**。合成音更清晰，真人音有音高变化、语速波动、口音。
   这不是模型退化，是**测量口径变准了**。

2. **noisy 条件（10 dB）很可能不过 80% 阈值**。真人语音在 10 dB 信噪比下的
   识别率天然低于安静环境。届时要做的是**决定阈值**，而不是**调模型**——
   因为近场拾音的部署形态里，10 dB 是不是必须支持的场景，是产品决策。

   真要调阈值，改的是 `core/eval/edge_eval.py` 里的 `MIN_ASR_ACCURACY`，
   并**同步** Java 侧的 `EvalGates.MIN_ASR_ACCURACY`（两处必须一致）。

## 8. 还没解决的（不是录音能解决的）

| 项 | 说明 |
|---|---|
| 端侧 ASR 在 Cortex-M 上的延迟 | 未在真机测量。见 `device-ref/README.md` 的「未验证项」 |
| 真人语音的**方言、口音、语速**覆盖 | 本次录音只覆盖一位朗读者的标准普通话 |
| 设备端真实拾音链路 | PC 模拟端的麦克风链路与真机的 I2S/DMA 差异未验证 |

前两项是**本次录音也覆盖不到**的，需要单独规划；
第三项属于真机联调，见 `device-ref/README.md`。

## 9. 出问题找谁 / 找哪

| 现象 | 去哪 |
|---|---|
| `--check` 说缺录音 | 文件名不对，用 `--list` 重新对照 |
| 报告里「音频来源」还是 TTS | 同上；或录音格式不是 16-bit 单声道（评测会明确报错） |
| 准确率明显偏低但音频来源是「真人录音」 | 可能是录音环境太吵（自带噪声 + 叠加噪声混了），重录 |
| 报告里出现「音频为 TTS 合成，不作门禁依据」 | 说明**不是全部**样本都是真人录音 —— 差一条就不会升级 |
